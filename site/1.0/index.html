kbagent · 1.0 compared with 0.100

kbagent 1.0 at a glance

kbagent 1.0 makes all commands follow the same rules. No command and no long option is removed. Two options get a new name, and the old names keep working for now. Some defaults, exit codes and messages change. The main changes come first, then the gaps that 0.x already closed, then the full list.

The main changes in 1.0

These are the changes that most often need a change in a script or an agent.

One rule for a missing --project, not three

0.x
What a command did without --project depended on the command. 172 commands stopped with an error, 25 used your active project, and 19 worked on every registered project, for example config list and job list. One of the 19 was workspace gc: without --project it deleted unused workspaces in every registered project.
1.0
Every command uses your active project when you leave out --project. Only --all-projects works on every project:
19 → 0commands that work on every project without being asked
25 → 223commands that use your active project
172 → 0commands that stop and ask for --project

Counts from kbagent 0.99 and 1.0. Commands that delete still ask first. Three commands use --project for something else: init, lineage show and agent prompt-improve.

What to do: choose your project once with kbagent project use. In scripts and agents, give --project on every command, because all your terminals and sessions share the active project. On the 18 read commands, --project and --all-projects already work on 0.100.

Deletes ask, scripts confirm with --yes

0.x
In a script, a confirmation took its answer from the input: echo y | kbagent ... confirmed a delete. branch delete and workspace delete deleted at once, with no question and no --dry-run.
1.0
Without a terminal, the command stops unless you give --yes. branch delete and workspace delete ask, and take --yes and --dry-run. --json still counts as a confirmation.

What to do: add --yes to scripts that confirm.

Mistakes stop before they change data

0.x
A single-value option given twice used the last value with no message: --project x ... --project test acted on test. --text @notes.md saved the file name, not the file.
1.0
Both are errors, and the message says what to fix. On read commands, an option given twice only adds a warning.

What to do: give a single-value option once. Use --file for text from a file.

One short flag for each option, on every command

0.x
A short flag worked on some commands and not on others, and seven short flags meant different options in different commands. For example, -d was --directory, --body, --deny or --description.
1.0
Each short flag means one option, and every command with that option accepts it:
24 → 228-p for --project
2 → 40-n for --name, as in the Azure CLI
1 → 20-t for --type
0 → 14-L for --limit, as in the GitHub CLI

Commands that accept the short flag, before and after. Removed, because they meant a different option in some commands: -c and -r everywhere, and -d, -f, -l, -m, -n and -v where they did not mean --directory, --feature, --load, --message, --name and --verbose.

What to do: replace a removed short flag with the long option name. Long names work on 0.x and on 1.0.

A failure is never reported as success

0.x
A read across projects ended with exit code 0 when one project failed. The same error could end with different exit codes in different commands.
1.0
Exit code 1 after the full output. Each error code has one exit code, in one published list.

What to do: check scripts that test for a specific exit code.

--json always answers in JSON

0.x
A typo, a wrong value or a crash printed no JSON. --json worked only before the command.
1.0
Every run prints one JSON document, errors included. Only --help still prints help, and a --stream command still prints one JSON line per event. kbagent config list --json works too.

What to do: read error.code for every exit code.

One word for one thing

0.x
The project you chose with project use was the "pin" or the "default project". The branch you chose with branch use was the "active branch", and the REST API called it "pin" too:
pindefault projectactive branch
In Keboola, "default branch" already means the production branch.
1.0
One name everywhere:
active projectactive branch
project use prints Active project: prod. The JSON fields and the configuration file do not change.

What to do: nothing, unless a script reads the text of project use.

kbagent serve follows the same rules

0.x
Over HTTP, 26 routes used production and list routes read all projects, while the command line used the active branch and project. Most errors answered HTTP 502.
1.0
The same project and branch as the command line, HTTP status codes that match the error, and PATCH for partial updates.

What to do: send branch_id: 0 for production and all_projects=true for all projects.

  • No command removed or renamed, no long option removed
  • No JSON field removed or renamed
  • No new exit codes (still 0 to 7 and 130)
  • Python SDK unchanged

Dangerous gaps that 0.x already closed

These could delete data, act on the wrong project, or let a command through a safety setting. They did not wait for 1.0: kbagent 0.96 to 0.100 fixed them. If you run an older 0.x version, update.

Fixed in 0.100.0

Safety options that did nothing

Before
storage delete-bucket and storage file-delete had a --yes option, but never read it. They deleted without asking. delete-bucket --force also deleted a shared bucket, although the help says to unshare it first.
Now
Both ask in a terminal, and --yes skips the question. --force no longer deletes a shared bucket.
Fixed in 0.96.1 to 0.100.0

A permission setting with gaps

Before
--deny-writes, --deny-destructive and saved permission policies did not apply to kbagent http and kbagent search, so kbagent http delete ran under --deny-destructive. --deny-destructive also did not stop sync push --force, a token refresh or a password reset. Over kbagent serve, only two groups of routes were checked.
Now
Every command and every kbagent serve route is checked, except the health and documentation routes. Commands that reset a password, invalidate a token or replace all variables count as destructive.

Other dangerous behavior that 0.x fixed

  • workspace gc without --project deleted unused workspaces in every registered project. When it could not list the configurations of a project, it took every sandbox workspace in that project as unused. 0.100.0
  • sync push --project B in a folder of project A created the configurations of project A in project B. 0.100.0
  • sync push deleted a configuration in Keboola when its local folder was missing, also without --force. 0.96.1
  • A second flow delete of the same flow removed it from the trash for good. 0.100.0
  • job run --idempotency-key, repeated after a lost answer, started a second job. 0.100.0
  • Over kbagent serve, DELETE /flows/...?dry_run=true ran the real delete. 0.100.0
  • Removing the active project made the next project active without a notice. 0.100.0
  • Commands used the branch from branch use and did not say so. Now each command names the project and branch it uses. 0.96.1
  • data-app password printed the password, so it went into an AI agent's chat history. Now it prints the password only with --reveal. 0.96.1
Other changes in 0.x
  • Commands that change several items end with exit code 1 after a failed item (0.98.0).
  • --project also accepts a project ID (0.96.1).
  • --all-projects on the 18 read commands, so one script works on 0.x and on 1.0 (0.100.0).
  • kbagent update stays on 0.x until the move date. kbagent update --major moves earlier (0.100.0).

When 1.0 reaches you

Release day

New installs get 1.0

Install script, PyPI, Homebrew, apt and rpm (Chocolatey and winget after their package review). Also CI pipelines that install kbagent without a version, and package-manager upgrades.

The next 28 days

Installs that update themselves stay on 0.x

kbagent 0.100 and later shows a notice with the move date. kbagent update --major moves to 1.0 at once.

Day 28

They move to 1.0

An install that updates itself moves to 1.0, also a version older than 0.100. The first command that changes data after the move stops once and links to the migration guide.

To stay on 0.x, set KBAGENT_AUTO_UPDATE=false. In CI, also install keboola-cli<1. A Homebrew, apt, rpm, Chocolatey or winget package stays on 0.x with a hold in the package manager, for example brew pin or apt-mark hold. 0.x gets security and data-loss fixes until day 28.
